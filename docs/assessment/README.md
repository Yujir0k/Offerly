# Профессиональная проверка в Офферли

Встроены неизменённые текущие исходники **formal-generator-7.3.3 / competency-4**. Серверный AdaptiveService работает через транзакционный адаптер PostgreSQL; архивная SQLite-авторизация и демонстрационные аккаунты не подключаются. Новый production-пакет не добавлен.

Открыть: кабинет кандидата → «Проверка навыков», `/demo/candidate/assessment`. Выбор всех 12 специализаций и Junior/Middle/Senior; продолжение по `?session=...`. «Результаты» показывает отчёты и историю; старые прототипные проверки сохранены отдельно. Кандидатский грейд определяется четырьмя компетенциями исходного движка, а не процентом верных ответов. Число 0–100 в существующем индексе ранжирования — нормированная взвешенная оценка свидетельств, не доля правильно решённых вопросов.

## Запуск

Из корня `offerly-web`:

```sh
npm ci
npm run dev
```

Нужен Node.js >=22.17.0. Существующий npm lock сохранён: зафиксированные зависимости не обновлялись. `predev` и `prebuild` компилируют vendor через уже установленный TypeScript. Можно использовать соответствующие `pnpm run dev` / `pnpm run build` после установки тех же зафиксированных зависимостей; не выполнять независимое обновление версий ради интеграции.

Локальный адрес — `http://localhost:5173`. В разработке без DATABASE_URL используется прежняя PGlite-база, миграция 008 применяется автоматически. На PostgreSQL:

```sh
npm run db:migrate
npm run build
npm run start
```

Прежние DATABASE_URL, APP_URL, настройки почты, cookie и файлов остаются прежними. Для production нужен настроенный PostgreSQL, как и до интеграции. Архивная SQLite не является production-хранилищем Офферли.

## Переменные и миграция

- Новые обязательные секреты или переменные отсутствуют.
- `GENERATIVE_POOL_FILE` — исходная необязательная переменная готового проверенного пула. По умолчанию не задаётся: генерация работает локально по формальным моделям, без внешней LLM.
- `calibratedForms` **выключен** исходным default; клиент не может включить его или подменить конфигурацию. 90-дневное ограничение не применяется.
- `008_professional_assessment.sql` добавляет `professional_assessment_records` и таблицу блокировок. В records сохраняются целые снимки с FK пользователя и scope, экспозиции и резервы видимых вопросов. Старые таблицы/пользователи/результаты не удаляются.
- Один активный снимок на пользователя; блокировка аккаунта и согласованный порядок блокировок tracks защищают создание, ответы, expiry и резервы в нескольких серверных процессах. При удалении аккаунта удаляются новые приватные записи; запрос, ожидавший блокировку, не может создать данные удалённого аккаунта.
- Результат и публичная проекция фиксируются один раз. Завершённые попытки не переоцениваются. Версия генератора, blueprint, конфигурация scoring/калибровки и все задания остаются в серверном снимке.

## API и права

Для всех методов нужна настоящая сессия Офферли, подтверждённая почта (кроме существующего приватного demo) и кандидатский контекст `X-Offerly-Role: candidate`. POST также проверяет Origin. У аккаунта Офферли два кабинета; заголовок обозначает рабочий контекст, а не выдаёт права другого пользователя. Чужой sessionId всегда закрыт.

| Метод | Путь относительно /api/professional | Результат |
|---|---|---|
| GET | /generative-packs | 12 публичных специализаций и описание |
| GET | /adaptive-sessions | Собственная история |
| POST | /adaptive-sessions | specialization, targetGrade → новая попытка/та же активная |
| GET | /adaptive-sessions/:id | Публичный текущий шаг либо сохранённый отчёт |
| POST | /adaptive-sessions/:id/answer | itemId, stepId, optionId, execution → следующий шаг |
| POST | /adaptive-sessions/:id/evidence | itemId, stepId, artifactId → открытый источник |

Точный повтор сохранённого ответа идемпотентен; другой ответ на уже записанный шаг — 409. Восстановление после reload сохраняет серверный шаг и публичный локальный черновик. Таймер проверяется сервером **после ожидания транзакционных блокировок**, не по времени прихода запроса; новый ответ после deadline не принимается. Expiry и освобождение резервов выполняются при обращении, обязательно перед новой выдачей того же track/grade.

Seed, ground truth, rubric, accepted plans, численные параметры калибровки и служебная телеметрия не выдаются клиенту. Код генератора не входит в клиентские JS-чанки. Административные маршруты архива не публикуются: существующая платформа не имеет admin-роли, и пользователь отложил админку. Не добавлены архивные login/demo/bridge/profile-result endpoints. Старые start/answer/finish в /api/action закрыты, чтобы прототипный порог 75% не обходил формальную проверку.

## Границы и дальнейшие обновления

Общие шапка, sidebar, лендинг, регистрация и другие кабинеты сохраняют дизайн. В layout подключён один изолированный CSS-файл: **все его селекторы ограничены .formal-assessment**, вне раздела он не меняет оформление. Обновление метаданных устройств, очистка приватного черновика при смене аккаунта, расширение серверной валидации полученной специализации и привязка результата — необходимые технические изменения.

Не заменять vendor другой методикой под активными сессиями. Новую ревизию нужно хранить отдельно и маршрутизировать исполнение по generation.generatorVersion. Неизвестная активная ревизия сейчас вызывает явный 409, вместо незаметного оценивания новым кодом. Для завершённых отчётов используется сохранённая публичная проекция. Интеграция не подключает SMTP/домен/ФСП ID заново и не является нагрузочной проверкой реального VPS.

## Сохранённые источники и доказательства

Исходный ZIP сохранён без изменений; полная распаковка находится в `work/fsp-assessment-7.3.3-original` в корне проекта. В ней остаются все исторические snapshots, locks, калибровочные данные, исследования и references. В vendor находятся актуальные исходники, тесты, исходный lock, документы и исходная tsconfig отдельно от интеграционной. CRC всех 6768 файлов и SHA-256 ZIP проверены; manifest — verification/archive.json.

Для переноса всего проекта на другую машину включить **исходный ZIP/полную распаковку доказательств**, не только runtime app. Runtime не зависит от абсолютных путей. Для воспроизведения исходных тестов из `offerly-web`:

```sh
npm run assessment:build
npm run test:assessment
```

Скрипт сам выбирает рабочую папку полной исходной распаковки: тесты читают исторические locks относительно неё. Если распаковка находится в другом месте, задайте `ASSESSMENT_REFERENCE_DIR` на каталог с `data/synthetic-validation/BASELINE_LOCK.json`. Для целевого прогона можно передать имена: `npm run test:assessment -- domain.test.js session.test.js`. Наличие всех исследовательских файлов в runtime vendor не требуется; исторические locks никогда не генерируются вместо оригиналов.

Тесты читают сохранённые evidence/locks из исходного каталога; не запускать тяжёлые исследования заново. [Карта переноса](transfer-map.md), [отчёт о проверках и ограничениях](verification-report.md).

Отдельный NEXT_AGENT_7.3.3.md не найден в архиве и среди приложений. Изучены AGENT_HANDOFF, PORTABLE_START, README, ASSESSMENT_FINAL, ТЗ/references и расшифровка Q&A; пользовательский подробный промпт имеет приоритет. Если отдельный handoff будет прислан позже, его нужно дополнительно сверить с этой интеграцией.

## Повторить проверки переноса через HTTP

Работать только в отдельной копии приложения. В копии создать `app/api/qa-assessment/route.ts` из `qa/assessment-fixture-route.ts` и включить `ENABLE_ASSESSMENT_QA=true`. Этот тестовый маршрут дополнительно блокирует production и нелокальные адреса; он намеренно возвращает закрытый снимок **только собственных синтетических аккаунтов** для сравнения с эталоном. В основном app/api его нет. После проверки удалить маршрут и выключить флаг.

Для копии использовать отдельный PGLITE_PATH, APP_URL=http://127.0.0.1:5174, MAIL_TRANSPORT=file, ENABLE_DEMO=true. После `npm run assessment:build` запуск на5174: `node node_modules/next/dist/bin/next dev --webpack -H 127.0.0.1 -p 5174`. Копия должна содержать скомпилированный vendor; реальные пользовательские данные/секреты туда не копировать.

Из основного `offerly-web` (заменить относительный путь mailbox, если копия названа иначе):

```sh
TEST_MAIL_DIR=../work/assessment-qa/.data/mail-outbox node qa/assessment-prepare.mjs
node qa/assessment-transfer-check.mjs
node qa/assessment-boundary-check.mjs
node --import tsx qa/assessment-artifacts-check.tsx
node --import tsx qa/session-device-check.ts
```

Первый transfer-запуск проходит36 сценариев; при возобновлении уже сохранённые завершённые сценарии сохраняются в отчёте, а активная попытка продолжается. Для чистого повторения подготовить новые синтетические аккаунты. Файлы временного контекста содержат только тестовые секреты и имеют mode0600. Повторные тесты не являются новым holdout/исследованием точности.
