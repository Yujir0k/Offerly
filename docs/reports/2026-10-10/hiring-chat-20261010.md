# Подбор, приглашения и переписка — 10.10.2026

## Рабочий сценарий

Работодатель заполняет компанию и создаёт подборку: специализация, подтверждённый грейд, технологии, зарплатная вилка и формат. Подборка приватная: это критерии поиска, она не рассылается всем кандидатам. Для публичного предложения нужно создать и опубликовать вакансию. Она появляется в каталоге соискателя и учитывается в подходящих предложениях; отдельное приглашение отправляется выбранному человеку.

В каталоге участвуют заполненные профили с подтверждённым тестом грейдом, согласием на публикацию и включённым поиском. Заявленный грейд не считается подтверждённым. Неподтверждённый кандидат может заполнить профиль и пройти испытание. Неудачный тест не стирает прежнее подтверждение; изменение специализации требует нового подтверждения.

Для приглашения нужны подтверждённая почта работодателя, права компании, её название/описание/контакт, описание роли, положительная зарплата от–до и способ связи. Сервер запрещает чужую подборку, приглашение себе, неподходящий по доступности профиль и повтор активного приглашения. Приглашение сохраняет needId и снимок соответствия, если отправлено из подборки. Получатель изучает условия и принимает/отклоняет. Просмотр не раскрывает контакты; принятие раскрывает телефон и почту только участвующей компании.

После принятия появляется «Открыть чат». Он также доступен из самостоятельного отклика на опубликованную вакансию с согласием на передачу контактов. Диалог общий для пары компания–кандидат; новые приглашения/отклики не создают дубликаты. Обе стороны видят его в разделе «Сообщения».

## Ранжирование

Это объяснимая эвристика подбора, не изменение формальной методики оценки грейда:

- 50 баллов за точное совпадение специализации и подтверждённого уровня;
- до 30 за технологии: проверенная технология имеет вес 1, указанная кандидатом — 0,5;
- до 15 за результат проверки;
- 5 за существующую историю достижений ФСП; введённый ID без истории не даёт бонус.

Формат и пересечение зарплатных ожиданий используются в фильтрации подборки. Фильтр «подтверждённые навыки» требует проверенных технологий. Нельзя выдавать самоописание за сертификацию отдельных технологий: тест подтверждает категорию, а не автоматически все навыки из профиля. Совпадение в каталоге и снимок в приглашении используют одну шкалу. Подбор — рекомендация работодателю, он сам выбирает адресата и условия.

## Хранение и права

Миграция `db/migrations/009_conversations.sql`: conversations, conversation_messages, conversation_reads, внешние ключи, индексы, уникальность пары и клиентского ID сообщения. Миграция добавляет таблицы без удаления существующих пользователей/результатов. При удалении аккаунта его диалоги и сообщения удаляются каскадно вместе с рабочими данными; политику резервных копий нужно определить при развёртывании.

Локально PGlite применяет миграции при первом соединении после перезапуска. Для PostgreSQL до запуска новой версии выполните `npm run db:migrate` с DATABASE_URL; Compose уже запускает отдельный migrate-сервис. Новых переменных окружения или зависимостей чат не требует.

Cookie существующей авторизации, серверная проверка владельца профиля/членства в компании/scope. Заголовок роли не выдаёт права. Owner/recruiter отправляют сообщения; viewer только читает существующие диалоги. Интерфейс управления коллегами пока не входит в этот объём. Чужие/удалённые аккаунты и другой демо-scope не получают доступ. Письмо должно быть подтверждено перед началом общения и записью. Нет общего поиска адресатов для произвольной рассылки.

Сообщения до 4000 символов выводятся обычным React-текстом, без HTML. POST проверяет Origin, ограничивает размер потока тела и частоту запросов. Транзакция блокирует диалог на время отправки. Повтор с тем же clientId и текстом возвращает прежнее сообщение; другой текст с тем же ID даёт 409. Клиент сохраняет ID для повтора при сетевой ошибке. Отметка прочтения монотонная, проверяется принадлежность сообщения диалогу. Чужие клиентские ID и скрытые ключи тестов не попадают в ответы.

## Интерфейс/API

- Список 30 диалогов с nextCursor, сообщения по 40 с before; более ранние сообщения загружаются отдельно.
- Непрочитанные, контекст приглашения/отклика, дата, автор, отправлено/прочитано, отдельные пустые состояния.
- Enter отправляет, Shift+Enter переносит строку; черновики в sessionStorage отдельно для аккаунта/диалога, сохраняются при обновлении вкладки.
- На телефоне список и диалог открываются последовательно. Проверены 1280×720 и 390×844 без горизонтального переполнения и с доступной кнопкой отправки.
- Обновление активной переписки раз в 3 секунды, списка раз в 5, счётчика раз в 15; скрытая вкладка пропускает обновления. Онлайн-статусы не выдумываются.
- `GET /api/conversations` — список, `?summary=1` — счётчик, `?before=nextCursor` — следующая страница.
- `POST /api/conversations` — `{invitationId}` или `{applicationId}`, возвращает `{id}`.
- `GET /api/conversations/{id}` — conversation/messages/hasOlder/otherReadThrough; before — строковый ID самого раннего сообщения.
- `POST /api/conversations/{id}` — `{type:"message", body, clientId}` или `{type:"read", through}`.
- Для всех ручек X-Offerly-Role: candidate/employer, существующая cookie; POST с допустимым Origin. OpenAPI дополнен.

Правая панель испытания снова sticky. Таймер и прогресс остаются видимыми; длинная навигация имеет собственную прокрутку. Сохранённый ответ можно изменить до завершения. Снятие ответа снижает прогресс, повторное сохранение возвращает его. Дизайн опроса не менялся.

### Повторение HTTP-проверок

Только на отдельной localhost-копии с отдельной БД и MAIL_TRANSPORT=file. Установите ENABLE_ASSESSMENT_QA=true и скопируйте `qa/assessment-fixture-route.ts` в `app/api/qa-assessment/route.ts` **только в этой QA-копии**. У fixture есть проверки NODE_ENV, loopback и префикса synthetic email; в production её нельзя устанавливать. Она позволяет проверить приватное серверное состояние собственных тестовых попыток и назначить роли синтетическим участникам компании для отрицательных проверок. После QA удалите эту временную ручку до сборки.

```
TEST_BASE_URL=http://127.0.0.1:5188 TEST_MAIL_DIR=путь-к-QA-mail-outbox node qa/hiring-chat-check.mjs
TEST_BASE_URL=http://127.0.0.1:5188 TEST_MAIL_DIR=путь-к-QA-mail-outbox node qa/platform-check.mjs
TEST_BASE_URL=http://127.0.0.1:5188 TEST_FIXTURE_FILE=/tmp/offerly-hiring-users.json node qa/chat-boundary-check.mjs
# После перезапуска той же QA-копии/БД:
TEST_BASE_URL=http://127.0.0.1:5188 TEST_FIXTURE_FILE=/tmp/offerly-hiring-users.json TEST_AFTER_RESTART=1 node qa/chat-boundary-check.mjs
```

hiring-chat-check сохраняет только синтетические учётные данные в /tmp с mode 0600, вне репозитория. Приватный fixture-файл не передавать в архив поставки. Основное приложение не содержит диагностическую ручку.

## Границы MVP

Чат текстовый, без вложений, звонков, редактирования/удаления отдельных сообщений, жалоб/блокировок и push-уведомлений. SMTP/домен/VPS не подключались. Для больших объёмов одновременных переписок нужно измерить нагрузку на целевом PostgreSQL и заменить частый polling на SSE/WebSocket/очередь уведомлений при необходимости; текущие проверки не доказывают production-ёмкость. Модерация работодателей и приглашение коллег в интерфейсе остаются отдельными задачами.
