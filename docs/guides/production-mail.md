# Фирменные письма и SMTP

Отправитель: `Офферли <noreply@opherly.ru>`. Это адрес отправки, не входящий почтовый ящик. Postbox не хранит входящие ответы. Reply-To пока не задан; для поддержки сначала нужно создать реальный входящий ящик (например, отдельно в Яндекс 360), а затем добавить его в транспорт. Адрес получателя тестовых писем не становится отправителем сайта.

## Выбранный провайдер — SMTP.BZ

Для нового подключения используйте данные из «Подключение и квота → SMTP»:

```dotenv
APP_URL=https://opherly.ru
MAIL_FROM=Офферли <noreply@opherly.ru>
SMTP_HOST=connect.smtp.bz
SMTP_PORT=465
SMTP_USER=<логин SMTP из панели провайдера>
SMTP_PASSWORD=<отдельный пароль SMTP из панели провайдера>
MAIL_WORKER_ENABLED=true
```

Проверяйте TLS-сертификат; порт 465 использует TLS сразу, 587 — обязательный STARTTLS. Пароль хранится в приватном env вне Git с правами 600. SMTP-логин не является получателем писем или отправителем сайта.

В DNS нужны TXT `smtpbz._domainkey` с полным ключом из панели, единственная TXT SPF на `@` с разрешёнными источниками и CNAME `stats` → `smtp.bz.`. На последней проверке сервис обнаружил три записи, но домен ещё на модерации. После её завершения нужно проверить соединение с VPS, реальную доставку, DKIM/DMARC и лимиты именно аккаунта. В панели показано 100 писем в час; счётчики приложения не заменяют квоту провайдера. До подтверждения соединения и доставки миграцию нельзя считать завершённой.

## Предыдущий провайдер — Yandex Cloud Postbox

1. Создать адрес домена в Cloud Postbox и сохранить обе CNAME-записи DKIM у DNS-провайдера. Дождаться статуса `Success`. SMTP-авторизация может работать до подтверждения домена, но отправка будет отклоняться: `550 5.4.1 identity not verified`.
2. Сервисному аккаунту в том же каталоге назначить `postbox.sender` и создать API-ключ с областью `yc.postbox.send`.
3. В приватном окружении сервера задать:

```dotenv
APP_URL=https://opherly.ru
MAIL_FROM=Офферли <noreply@opherly.ru>
SMTP_HOST=postbox.cloud.yandex.net
SMTP_PORT=465
SMTP_USER=<идентификатор API-ключа>
SMTP_PASSWORD=<секрет API-ключа>
MAIL_WORKER_ENABLED=true
```

Пароль личного аккаунта Яндекса и идентификатор сервисного аккаунта для SMTP не используются. Секреты хранить вне Git и сборочного контекста, права файла 600. Нужен исходящий доступ VPS к SMTP 465; транспорт проверяет TLS-сертификат. Альтернатива — порт 587 с обязательным STARTTLS.

4. Перед выкладкой сделать backup базы и окружения, применить миграцию `022_invitation_mail.sql`, затем запустить новый релиз. Проверить health и доставку. Старые приглашения автоматически не рассылаются.

## Сценарии

Один фирменный шаблон используется для подтверждения регистрации, проверки старого адреса, подтверждения нового адреса, восстановления пароля, уведомления об изменённом пароле и нового приглашения. HTML сопровождается текстовой версией; знак A6 нарисован цветными ячейками HTML-таблицы 40×40, без внешних картинок, фоновых изображений и вложений. Название и код остаются текстом. Этот способ проверен в Chromium без сетевого доступа на ширинах 640 и 390; отображение в конкретном почтовом клиенте подтверждается отдельно. Аватар отправителя настраивается отдельно от шаблона; для Gmail BIMI требует VMC/CMC и DMARC quarantine/reject. Код — копируемый текст, не картинка. В письме приглашения нет скрытых контактов работодателя; ссылка ведёт к конкретному приглашению и сохраняется при входе.

Коды отправляются сразу. Уведомление о приглашении сохраняется в транзакционной очереди вместе с приглашением. Worker проверяет очередь каждые 30 секунд; сбой SMTP не отменяет само приглашение. Повторы с задержкой, максимум восемь попыток; после перезапуска просроченная аренда задания восстанавливается. Доставка имеет семантику at-least-once: стабильный Message-ID помогает почтовым клиентам, но не гарантирует отсутствие дубля при сбое между принятием письма SMTP и фиксацией результата в БД.

Перед отправкой заново проверяются адрес, статус приглашения, блокировки, принадлежность аккаунтов, подтверждение почты и настройка «Приглашения по почте». Демонстрационные аккаунты не получают рассылку. Отмена, удаление, принятие или отказ до отправки подавляют уведомление; редактирование не создаёт новую рассылку. Отложенные уведомления учитывают паузу пользователя. В логах очереди сохраняется класс ошибки без кода подтверждения, SMTP-текста и адреса получателя.

## Проверки

```sh
npm run test:mail
npm run check:types
```

Интеграционная проверка `qa/mail-scenarios.mjs` требует отдельного локального сервера на 127.0.0.1 с изолированной БД и отдельного Mailpit. Она создаёт собственные аккаунты и проверяет настоящие API регистрации, смены адреса, восстановления, входа и приглашения, а также фактический MIME. Никогда не открывать рабочую PGlite другим процессом. Приватные результаты (OTP, cookie, аккаунты) находятся вне проекта, в домашнем `.cache/offerly/private-mail/`; не публиковать их.

По умолчанию реальные письма не отправляются. Режим пересылки на внешний адрес требует явного разрешения получателя и отдельного ограниченного SMTP relay. SMTP acceptance не доказывает появление письма во входящих: отдельно проверяются почтовый ящик, спам, оформление на мобильном и заголовки DKIM/DMARC.

Официальные инструкции: [подтверждение домена](https://yandex.cloud/ru/docs/postbox/operations/check-domain), [начало работы и SMTP](https://yandex.cloud/ru/docs/postbox/quickstart).

Настроить в Рег.ру (не создавать вторую SPF-запись, если она уже появилась): TXT `@` → `v=spf1 include:spf.postbox.yandexcloud.net ~all`; TXT `_dmarc` → `v=DMARC1; p=none`. Это начальная политика наблюдения. [Инструкция Яндекса](https://yandex.cloud/ru/docs/postbox/concepts/dns-records). Корневой SPF не совпадает с прежним SPF PASS для технического Return-Path провайдера.
