# ФСП ID / Keycloak

08.10.2026. Рабочий OIDC-клиент подготовлен, внешний сервис ФСП не подключён. На входе и регистрации видна кнопка с оригинальным логотипом из брендбука. Пока `FSP_OIDC_ENABLED=false`, кнопка кликабельна и ничего не делает: без переходов, всплывающих сообщений и новых надписей. В настройках есть привязка к существующему аккаунту; демо остаётся отдельным реестром.

## Реализованные ручки

| Метод | URL | Ответ / доступ |
|---|---|---|
| GET | `/api/identity/fsp` | Доступность подключения и собственная привязка, без секретов и чужих данных |
| POST | `/api/identity/fsp/start` | `{intent:"login"|"register", role, consent}` → authorizationUrl; Origin обязателен |
| POST | `/api/identity/fsp/link` | Начало привязки только к текущему обычному аккаунту с подтверждённой почтой; Origin обязателен |
| GET | `/api/identity/fsp/callback` | Ответ провайдера → проверка → локальная сессия или фиксированный код ошибки; HTTP 303 |

Без настройки start/link возвращают 503/unavailable. Недействительная сессия для привязки — 401, неверное согласие — 400. Callback не принимает произвольный returnTo; пути выбирает сервер. Подробности схем — `openapi.json`.

## Что понадобится от ФСП

1. Issuer конкретного realm, например `https://id.example/realms/fsp` — это пример, не известный адрес ФСП.
2. Зарегистрированный client ID для Офферли; client secret для confidential client (или public client без секрета).
3. Разрешённый callback: `https://ваш-домен/api/identity/fsp/callback`, точный URL без wildcard.
4. Standard Flow (Authorization Code), PKCE S256, scopes `openid profile email`, подпись ID Token RS256.
5. Согласованный claim ID участника. `FSP_OIDC_PARTICIPANT_CLAIM=fsp_id` — настраиваемое предположение, не официальный контракт. Допускается строка либо безопасное целое число. Subject `sub` и issuer — основной ключ входа, они не равны ID соревнований.
6. Требования к `email_verified` и отдельный договорённый API истории достижений.

Параметры: `FSP_OIDC_ENABLED`, `FSP_OIDC_ISSUER`, `FSP_OIDC_CLIENT_ID`, `FSP_OIDC_CLIENT_SECRET`, `FSP_OIDC_PARTICIPANT_CLAIM`, `APP_URL`. Они передаются серверу в Compose, секреты не доступны браузеру. В production URL только HTTPS. `FSP_OIDC_ALLOW_LOCAL_HTTP=true` допускается исключительно в development на loopback для тестового провайдера; в production эта возможность не действует.

## Обмен и защита

1. Сервер проверяет Origin, намерение и согласие, лимит попыток; привязка требует собственной подтверждённой сессии и повторного входа у провайдера.
2. Discovery загружает конфигурацию issuer. Для Keycloak authorization/token/JWKS endpoints должны оставаться на том же origin. Timeout 10 секунд, конфигурация кешируется на 15 минут.
3. Генерируются случайные state, nonce, PKCE verifier/challenge S256 и browser-token. В DB хеши state/browser, verifier/nonce с TTL 10 минут; в HttpOnly/SameSite Lax cookie только browser-token. Для привязки сохраняется хеш исходной локальной сессии.
4. Callback атомарно потребляет попытку, проверяет браузер и срок, обменивает code сервером. `openid-client` проверяет issuer/audience/nonce/expiry; включена дополнительная проверка JWS-подписи через JWKS. Пароли ФСП, access/refresh/id tokens не сохраняются в браузере или БД.
5. `issuer+sub` однозначно связывается с user_id, одна привязка на issuer/аккаунт. Транзакции, ограничения уникальности и advisory lock исключают дубли при одновременных входах. Совпадение email не объединяет аккаунты автоматически.
6. Новый пользователь создаётся только после согласия на регистрации. Вход неизвестного пользователя ведёт к согласию, а не создаёт аккаунт незаметно. При `email_verified=true` доверенного провайдера почта считается подтверждённой; иначе открывается обычное подтверждение почты. Без email предлагается обычная регистрация с последующей привязкой.
7. Первый вход ведёт к анкете кандидата/компании, повторный — к обзору. Привязка сохраняет текущий аккаунт и его данные. Демо не привязывается к настоящему провайдеру.

Callback не пишет токены/claims/описания провайдера в логи; его URL исключён из стандартных dev access logs Next. При настройке reverse proxy также не логировать query code/state. Истёкшие flows удаляются при старте новых попыток; перед production добавить регулярную очистку.

## Что не является интеграцией достижений

Вход подтверждает владение аккаунтом ФСП. ID участника записывается лишь из согласованного подписанного claim. Сам вход не выдаёт грейд, достижения или бонус ранжирования. Бонус истории и фильтр истории теперь требуют непустых achievements; один ID его не даёт. Демо-история сохраняется только в демо. API достижений ещё не предоставлен: адаптер/структуру согласовать отдельно. Никакие догадки об URL реестра не используются для сетевых запросов.

Локальный выход завершает сессию Офферли. Глобальный logout/backchannel logout и периодическое обновление реестра не подключены; это отдельная настройка после получения требований ФСП. Сейчас внешний Keycloak/его realm не развёртывался и реальным пользователем не проверялся.

## Проверка

`qa/fsp-mock-provider.mjs` — loopback OIDC-провайдер с RSA/JWKS и проверкой PKCE/client authentication; это тестовый протокол, не настоящий сервер ФСП или Keycloak. `qa/fsp-api-check.mjs` — 57 HTTP-проверок: создание/повторный вход, роли, отсутствие дублей, согласие, неподтверждённая почта, привязка, совпадение email без слияния, чужая привязка, повторная привязка другого ID, подпись/audience/nonce/expiry, PKCE, browser binding, replay, отмена, потеря сессии. Отдельно `qa/fsp-ranking-check.ts` проверяет отсутствие бонуса без достижений.

UI проверен в браузере на 1280×720 и 390×844: кнопка равна по ширине и высоте полям (54 px), отступ 24 px desktop / 20 px mobile, нет переполнения или изменений после нажатия при отключённом подключении. Обычный вход/демо сохранены.

Первичные источники: [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [openid-client и OIDC example](https://github.com/panva/openid-client), [исходный пример](https://github.com/panva/openid-client/blob/main/examples/oidc.ts). По исходному ТЗ обязательна связь с ID и корректное отсутствие истории; Keycloak указан как ориентир совместимости. Уточнения о внешнем стенде — `research/14-organizer-qa.md`.

Дополнительно: email демо не резервирует адрес для обычного аккаунта, частные демо-данные не объединяются с новым аккаунтом. Миграции 003/004 проверены на PostgreSQL 16; отдельный namespace-тест подтверждает сохранность демо и уникальность публичных адресов. Регрессия платформы (53 HTTP-операции), TypeScript и production build прошли.

## Демонстрация реестра — 10.10.2026

Исходное ТЗ прямо сообщает, что API и структура реестра не предоставляются, и разрешает собственные тестовые данные. Поэтому отсутствие настоящего сервиса не блокирует демонстрацию. MCP не является названием обязательного протокола в данном ТЗ: вход подготовлен через OpenID Connect/Keycloak, история — отдельный адаптер.

В демо: **Мой профиль → История ФСП**. Выбрать участника и нажать «Загрузить историю (демо)»:

- `FSP-DEMO-1042`: синтетическое второе место командного турнира;
- `FSP-DEMO-1043`: участник существует, достижений нет;
- «Без привязки ФСП»: убрать демопривязку и историю.

История, источник `demo` и дата синхронизации сохраняются на сервере. Неизвестный ID возвращает 404 и сохраняет прежнюю историю. Категория, оценки и подтверждённые технологии при привязке не меняются; ID без достижений не даёт бонуса. В обычном аккаунте демопривязка запрещена.

`lib/fsp-registry.ts` определяет внутренний интерфейс `FspRegistryAdapter.history()` и реализует фиксированный демореестр. Это точка замены источника данных, **не реализация пока неизвестного внешнего контракта**. Когда появится реальный API, потребуется его транспорт, авторизация, преобразование ответа в этот интерфейс и контрактные тесты. URL, поля и права организаторов заранее не выдумываем.

Дополнительные ручки Офферли (не адреса API ФСП):

| Метод | URL | Поведение |
|---|---|---|
| GET | `/api/identity/fsp/history` | Только собственные сохранённые ID/достижения/дата/источник. Без сессии 401 |
| POST | `/api/identity/fsp/history` | `{id:"FSP-DEMO-1042"}`; только демо, cookie+Origin; синхронизация фиксированного реестра. Обычный аккаунт: 503 без изменения данных |

Прежний `POST /api/action` с `type=fsp` использует тот же адаптер и допускает только кандидата в демо. Поля достижений из тела запроса игнорируются. Схема БД не менялась: метаданные сохранены в JSON профиля. Новых зависимостей нет.

Локальная проверка входа остаётся в `qa/fsp-mock-provider.mjs`: запустить `node qa/fsp-mock-provider.mjs`, а **в отдельной тестовой копии**, не меняя основной `.env.local`, установить `FSP_OIDC_ENABLED=true`, `FSP_OIDC_ISSUER=http://127.0.0.1:5290/realms/fsp`, `FSP_OIDC_CLIENT_ID=offerly-test`, `FSP_OIDC_CLIENT_SECRET=test-secret`, `FSP_OIDC_ALLOW_LOCAL_HTTP=true`, `APP_URL=http://127.0.0.1:5174`. Затем `TEST_BASE_URL=http://127.0.0.1:5174 node qa/fsp-api-check.mjs`. Секрет здесь — публичная фикстура, не ключ ФСП. Провайдер только loopback/development, не для публичного размещения. Обычная кнопка входа остаётся тихой при отключённом OIDC, как ранее запрошено пользователем.

Проверка новой истории: `TEST_BASE_URL=http://127.0.0.1:5174 node qa/fsp-history-check.mjs` на изолированной копии. Создаёт только тестовые аккаунты; основной 5173 запрещён скриптом. Правило повторных испытаний и архитектура нагрузки: [capacity-and-retakes.md](../architecture/capacity-and-retakes.md).
