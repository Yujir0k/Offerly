# Правила подбора и общения — employer-2

Разбор задачи выполняет `POST /api/task-brief`: локальные словари/правила, без внешних API, LLM, GPU и новых production-зависимостей. Он возвращает редактируемый `requirements`, цитаты `signals` и ограничения `warnings`. Однозначные hard-контексты и nice-to-have разделяются до фильтрации. Источники миграций и прямые исключения не участвуют в подборе. Синонимы и категории описаны в `lib/skills-ontology.ts`; группы PostgreSQL/MySQL и RabbitMQ/Kafka работают как OR. Нажатие на тег меняет обязательность.

Сначала каталог ограничивает scope, видимость/согласие, направление, выбранные уровни, обязательные технологии, формат и пересечение бюджета. Затем SQL `offerly_candidate_rank` ранжирует внутри сопоставимых категории и версии. Подтверждённые и заявленные уровни разделены; приоритет теста/ФСП сам по себе никого не исключает.

`R = 50T + 25F + 25K`, компоненты в [0;1]:

- T: сохранённый результат теста / 100. При выборе типов задач — среднее сохранённых качественных уровней компетенций с серверными весами; сочетание задач усредняет веса. Неподтверждённый грейд не получает T.
- K: `(обязательные совпадения + 0,25 × проверенные обязательные + 0,5 × желательные совпадения) / (1,25 × число обязательных + 0,5 × число желательных)`. Без технологий — 0. Группа OR считается одним требованием.
- F: `min(1, сумма(результат × релевантность) / 2)`. Победа 1, призовое место 0,8, участие 0,4. Релевантность: 1 по направлению, 0,75 по нужной/приоритетной технологии, 0,5 для общей истории без направления, иначе 0. Повторы ID не добавляются; источники claimed и один лишь ФСП ID бонуса не дают. Одна полностью релевантная победа добавляет 12,5 балла, приз — 10; максимум ФСП — 25.

Режимы «Сначала результаты теста» / «Сначала достижения ФСП» используют 100T / 100F вместо совместного R, сохраняя ограничивающие фильтры и разделение категорий. Рекомендации строятся из ограниченного пула каталога по нескольким приоритетам, без изменения этих правил. Политика не является вероятностью найма или автоматическим кадровым решением.

В поиске и каждой рекомендации `Profile.match_reasons` содержит:

- `stack_summary`: фактическое число совпадений обязательных требований и отдельно проверенных навыков.
- `grade_status`: подтверждённый результат либо заявленный уровень; симуляция остаётся подписанной.
- `fsp_achievement`: реальные названия/дисциплины учтённых событий и бонус текущего режима; `null` без релевантных событий. Демонстрационный источник указан явно.
- `budget_fit`: полное/частичное пересечение зарплатной вилки либо отсутствие бюджета. Частичное пересечение не называется полным соответствием.

Приглашение хранит серверный снимок `source` задачи/вакансии, выбранной через `needId`; чужой источник запрещён. Для несохранённой задачи разрешён валидированный `taskBrief` с общим названием. Снимок переживает редактирование/удаление источника. `createdAt` определяет число полных дней ожидания; `sent`/`viewed` показывают бейдж, `accepted`/`declined` — нет. Автоматического отказа/истечения срока не добавлено.

Открытие чата и каждая запись (`send`, `task-response`, `task-review`) требуют accepted-приглашения для пары компания/кандидат либо собственного отклика кандидата на вакансию компании. Старый диалог не даёт исключения. История остаётся доступной участникам, но `canWrite=false` убирает редактор/отправку задач. `canMessage` управляет кнопками в карточках/сравнении/рекомендациях; API самостоятельно повторяет проверку.

Миграция `013_matching_policy.sql` заменяет функцию и добавляет OR-helper. Старые миграции не изменены. Локальный PGlite применяет миграции при запуске; в PostgreSQL нужен штатный запуск `node scripts/migrate.mjs` перед выпуском. Реальный реестр ФСП остаётся неподключённым; локальный OIDC и история демо имеют явные источники.

Проверки: 54 unit/SQL; 105 HTTP сценария работодателя; 52 HTTP подбора; 37 HTTP исторических диалогов. `qa/legacy-chat-check.mjs --seed` запускается только при остановленном QA-сервере и создаёт исторический диалог в `.data/task-match-qa/postgres`; затем обычный запуск проверяет запреты без согласия, при sent/viewed/declined. Тестовые аккаунты и база изолированы от пользовательской.
