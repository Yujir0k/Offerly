# Защита от фиктивных предложений — концепция по ТЗ

10.10.2026. ТЗ допускает концепцию. Полная модераторская админка отложена пользователем; не заявляем несуществующую ручную проверку каждой компании.

Уже работают: подтверждение почты, настоящая company/membership принадлежность, owner/recruiter/viewer, закрытые контакты до согласия, обязательная положительная зарплатная вилка и описание, запрет активного дубля приглашения, Origin/лимиты, журнал приглашения и решений, приватные исходники резюме, блок-лист компаний. Аккаунт и собственная публикация не дают право писать всем кандидатам в чате: чат появляется после согласия или отклика. Достижения ФСП нельзя выдать за реальные простым вводом ID. Профессиональная категория формируется серверным испытанием.

Следующий слой для публичного запуска: entity verification (реквизиты/ИНН и домен, статус unverified/review/verified/suspended, источник и дата проверки), признаки риска (массовые однотипные приглашения, подозрительные ссылки, запрос оплаты/документов вне платформы, несогласованность условий), queue жалоб на job/invitation/message с причиной и immutable snapshot. Жалоба не автоматически доказывает нарушение и не автоматически удаляет предложение. Нужны rate limit, дедупликация, ACL заявителя/модератора, журнал решения и оснований. Проверка домена не доказывает добросовестность; ложные положительные решения должны обжаловаться.

Разбор: зарегистрировать случай → оценить срочность → при существенном риске ограничить новые сообщения/публикации → запросить пояснение компании → решение с основаниями → уведомить стороны → независимое повторное рассмотрение по апелляции. Администратор не должен произвольно видеть все приватные файлы; доступ к конкретному case логируется. Исторические сообщения сохраняются для разбора по утверждённой политике сроков, публичные API не раскрывают жалобы другой компании.

Архитектура: company_verifications, trust_cases, case_evidence, moderation_actions и appeals; отдельные права trust_reviewer/trust_admin, transactional outbox для уведомлений и retry, защита webhook/signature при подключении реестра. Заявитель видит статус своего обращения, компания — предъявленные основания без лишних данных заявителя, кандидат — честный статус проверки. Скрытие компании сейчас доступно; это личная настройка, не модераторский бан. Формы жалоб, очереди и проверка реквизитов в текущей версии не реализованы — для буквального дополнительного пункта ТЗ здесь предоставлена цельная концепция, а не имитация модерации.
