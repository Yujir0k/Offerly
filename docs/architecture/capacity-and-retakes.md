# Нагрузка и повторная проверка — актуально 10.10.2026

Обновление 11.10: оптимизация поиска установлена на VPS, короткий прогон чтения до 200 активных виртуальных клиентов прошёл без ошибок. Поиск кандидатов p95 607 мс, вакансии 511 мс при 200 клиентах. [Замеры, изменения и ограничения](../reports/2026-10-11/vps-performance.md). Это проверка двух QA-сессий на текущем каталоге, а не общий предел всех действий.

## Действующая политика

По последнему запросу пользователя ограничение включено на сервере. Прежнее временное разрешение неограниченных повторов отменено. Версия: `retakes-2026-10-10-v1`, код `lib/assessment-retakes.ts`.

- После подтверждения грейда: **90 суток** до новой проверки любого уровня по той же специализации, включая повтор того же уровня.
- После неудачи или недостатка доказательств: **7 суток** до повтора того же уровня по той же специализации. Другой уровень доступен сразу, если нет действующего 90-дневного ограничения.
- Другая специализация независима. Первая попытка доступна сразу. Неудача не понижает прежнюю подтверждённую категорию.
- Серверный timeout расходует попытку с момента исходного deadline, а не с момента обновления страницы. Обычная потеря сети не создаёт новую попытку: можно продолжить активную.
- Существующая активная попытка продолжается с исходным временем. Параллельные старты сериализуются блокировкой аккаунта, одинаковые возвращают одну сессию.
- `GET /api/professional/eligibility` возвращает доступность, причину и точную `nextEligibleAt`. Запрещённый POST старта — 429 / `ASSESSMENT_COOLDOWN`. Клиент показывает причину и дату по Москве; часы клиента не участвуют в решении.
- Исторические завершённые попытки участвуют в проверке интервала, но не переоцениваются и не перезаписываются. Новые попытки сохраняют снимок версии политики рядом с неизменной конфигурацией генерации/оценивания.

Схема БД не менялась: история уже хранит даты/решение в `professional_assessment_records`. Исторические locks и исходники vendor не изменены. Отдельного обхода через демо-кнопку для повторных попыток нет. Рекомендация 90/7 — выбранная продуктовая политика, не эмпирически доказанный оптимум. Административная отмена попытки из-за подтверждённого инфраструктурного сбоя пока не реализована; вручную очищать пользовательскую историю для обхода нельзя.

Проверки: 18 граничных утверждений, 12 транзакционных, 37 HTTP при внедрении. Проверены точная граница, другой уровень/направление, параллельный старт, commit истёкшей попытки при отказе, неизменность старого результата. Команды и дальнейшие границы — [финальный аудит](../reports/2026-10-10/tz-audit-final-20261010.md).

## Архитектура размещения

Уже реализованы Node.js, PostgreSQL для сервера, PGlite для одиночной локальной разработки, приватное хранилище файлов, пагинация каталога по 20, индексы, серверные права, сохраняемые сессии/попытки, транзакции и контроль повторных отправок. Cloudflare не нужен для запуска. Это основа, не гарантия пропускной способности любого VPS.

Для первого размещения: HTTPS reverse proxy → Node.js приложение → приватные PostgreSQL и файлы. При нескольких экземплярах приложения БД и файлы должны быть общими; PGlite для такого режима не подходит. Идентификаторы и права проверяются сервером независимо от экземпляра.

Текущий алгоритм генерации/оценки синхронный и работает в процессе приложения. **Изоляция в ограниченном пуле workers или отдельном сервисе пока не реализована.** Это главный кандидат на следующий шаг при замерах задержек: веб-процесс принимает запрос, ограничивает число работ, worker выполняет исходный движок без изменения правил, результат сохраняется атомарно. Очередь должна иметь предел, отмену до начала работы, идемпотентность и контроль версии алгоритма. Серверный срок испытания не переносится на клиент и не удлиняется из-за перезапуска. Конкретный размер пула выбирается по CPU/RAM, не по количеству зарегистрированных пользователей.

Чат сейчас использует опрос API. При росте можно сначала увеличить интервал неактивным вкладкам, затем вводить доставку событий; поддерживать несколько экземпляров нужно через общий транспорт. Отправка почтовых уведомлений и фоновые синхронизации при росте также должны идти через ограниченную очередь с повторными попытками.

## Как проверять без 50 людей

Одновременных пользователей воспроизводит нагрузочный клиент с разными тестовыми аккаунтами и cookie. Люди для этого не нужны. Отдельно измерять: поиск/фильтры, чтение и отправку сообщений, старт/ответ/завершение испытания, загрузку PDF; затем смешанный сценарий. Резкий старт 50 генераций сложнее 50 открытых страниц.

На выбранном сервере: разогрев → ступени 10/25/50 виртуальных пользователей → короткий пик → длительный прогон. Смотреть p50/p95/p99, ошибки, CPU/RAM, задержку event loop, соединения/блокировки PostgreSQL, время выполнения генератора и рост очереди. Тесты идут на отдельной копии, не на реальных профилях. Предварительная цель для обычного API — p95 до 1 с и без неожиданных 5xx; допустимый бюджет генерации уточнить по фактическим замерам. Это критерии приёмки, не уже полученные результаты.

Резервирование проверяется машинно: согласованная копия PostgreSQL и файлов → восстановление в отдельную среду → проверка связей, входа, файлов и результатов. Люди нужны для другой задачи: понятности интерфейса и пригодности вопросов/грейдов. Для первого пилота достаточно нескольких представителей уровней; 50 одновременных участников не являются условием такой проверки.
